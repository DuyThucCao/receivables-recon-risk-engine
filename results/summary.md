What the rules cannot resolve automatically:

- **transposed_id_with_twin_claim (no line control number)**: The identifier points nowhere and two claim lines share member, date, code and charge. Nothing in the remittance says which visit was paid, so the rule queues it as AMBIGUOUS for a person to check the payer's claim number (ICN) against the payer portal.
- **repeated_service_without_line_control + transposed or mangled claim id**: Two verbatim-identical remittance lines are only accepted as two services when the claim can be found and has two identical lines. If the claim number is unreadable, the second copy looks like a file duplicate and is excluded; the payer's own claim totals (CLP03/CLP04) would be needed to resolve it.
- **split_deposit_second_untraced**: The traced credit does not equal the payment and the untraced credit matches nothing on amount, so both credits go to UNAPPLIED_CASH (reason POSSIBLE SPLIT) and the payment to REMIT_NO_DEPOSIT. A person allocates them; the cash identity still ties because all three sit in explicit buckets.
- **equal_amount_provider_payment_untraced**: Two untraced credits of the same amount from the same payer a few days apart fit two payments equally well. Choosing the nearest date would usually be right but is a guess, so the rule queues both as AMBIGUOUS.
- **orphan reversals**: A reversal whose original posting never arrived (its remittance file is missing) cannot be paired; it is queued.
