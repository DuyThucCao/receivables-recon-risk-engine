# Design: Payment Reconciliation & Receivables Risk Engine

This file is the shared contract for everyone working on the repository. If code and this
file disagree, fix one of them in the same change and record why in `docs/decision_log.md`.

## 1. What the project is

A working tool that reconciles receivables three ways (what was billed ↔ what the payer said it
paid ↔ what arrived in the bank) and then answers seven decision questions on top of the
reconciled data. The core is industry-neutral. Healthcare claims are the demonstration data
set because one medical receivable passes through a hospital, an insurer, a bank and a drug
supplier.

The demonstration company is **fictional**: "Meridian Health System", six fictional payers,
one operating bank account, one drug wholesaler. Nothing here describes a real organisation.

Guiding rules, in priority order:

1. Start from the business flow and the raw documents, not from tools.
2. Reconciliation must tie out to the cent. It is the primary test of the whole project.
3. Every analysis answers a named question from a named job title.
4. Few tools. Each dependency needs a business reason.
5. Never present simulated results as observations about the real world.

## 2. Business flow

```
service delivered -> claim submitted (837-like) -> payer adjudicates
    -> remittance advice (835-like): paid / adjusted / denied, grouped under a payment trace number
    -> money arrives in the bank as lump-sum deposits (EFT or lockbox), one deposit may cover many remittances
    -> hospital posts cash, works denials (appeal / correct / write off)
drug purchased from wholesaler (invoice, lot, expiry) -> stored -> administered to patient
    -> billed on a claim line -> reimbursed later
```

## 3. Raw documents (the only inputs to the pipeline)

Generated by `src/recon_engine/datagen/` with a fixed seed into `data/raw/` as flat files that
imitate real exports: wide, repeated header fields, text dates, inconsistent identifiers.

| File | One row is | Reverse-engineered from |
|---|---|---|
| `claims_export.csv` | one claim service line, claim header repeated | CMS-1500 / UB-04 claim forms |
| `remittance_advice.csv` | one adjudicated service line on a remittance | remittance advice / EOB |
| `bank_statement.csv` | one bank transaction | bank statement export |
| `payer_contracts.csv` | one payer x procedure (or category) rate | contract fee schedule |
| `drug_purchase_invoices.csv` | one invoice line (drug, lot, expiry, qty, unit cost) | wholesaler invoice |
| `drug_dispense_log.csv` | one administration or waste event | pharmacy dispense log |
| `claim_status_history.csv` | one status change event for a claim | work-queue / clearinghouse status feed |

Scale target: about 30,000 claims / 70,000 claim lines over service dates 2024-01-01 to
2025-12-31, snapshot ("as-of") date 2026-03-31, so recent claims are still open. A full
rebuild must finish in a few minutes on a laptop.

Defects are injected deliberately and recorded in `data/truth/` (ground truth). **Pipeline code
must never read `data/truth/`; only tests and evaluation scripts may.** Defects to include:
duplicate remittance lines, partial payments, reversals followed by corrected reposts,
late adjustments and recoupments, mangled claim identifiers (padding, prefixes, transposed
digits), one deposit covering several remittances, deposits with no remittance (unapplied
cash), remittances with no deposit, date shifts between payer time zone and bank posting day,
truncated trace numbers in bank descriptions, payments below contract rate.

Every generator parameter lives in `config/calibration.yaml` with: value, `source_class`,
source reference, retrieval date. `source_class` is one of the five data labels in section 8.

## 4. Database

PostgreSQL 16. `src/recon_engine/db.py` returns a connection: it uses `DATABASE_URL` when set
(for example a hosted Postgres), otherwise an embedded server from `pixeltable-pgserver`.
The embedded data directory lives **outside** the repository, by default
`~/.cache/receivables-engine/pg` (override with `RRE_PG_DIR`), because the repository sits in a
cloud-synced folder with a long path containing spaces, which breaks Unix socket paths and
makes the sync client churn. All SQL lives in `sql/` as numbered files run in order by
`src/recon_engine/pipeline.py`. Files whose name starts with `0` (schemas, raw tables, parse
functions, rules and reference data) run before the raw files are landed; the rest run after.
Core SQL uses the same functions for a full rebuild and for incremental intake
(`stg.process_new()`, `core.process_new()`, `recon.run_all()`, `mart.refresh_q1()`); see
`docs/decision_log.md` D-004, D-005.

Schemas:

- `raw`: files as landed, all columns text, plus `_file`, `_row_no`, `_loaded_at`.
- `stg`: typed, trimmed, identifier-normalised rows; rejected rows go to `stg.reject` with a reason.
- `core`: one data model per business process (not a generic template):
  claim submission (`fact_claim_line`, `dim_payer`, `dim_procedure`, `dim_service_line`),
  remittance (`fact_remit_line`, `dim_reason_code`), cash (`fact_bank_txn`),
  claim life cycle (`fact_claim_event`), drugs (`fact_drug_purchase`, `fact_drug_dispense`,
  `dim_drug`), contracts (`dim_contract_rate`).
- `recon`: match tables (`claim_remit_match`, `remit_bank_match`), `exception_queue`,
  `claim_line_status`, `daily_recon`, `control_totals`, and the procedure
  `recon.close_day(p_date date)` that posts one day and refuses to close if totals do not tie.
- `mart`: OLAP outputs, one or more per decision question (section 6).

Reconciliation rules are data, not hard-coded branches: `recon.match_rule` lists rule id,
description, priority and tolerance; every match row stores the rule that produced it. A rule
accepts only a unique candidate; ambiguous items go to the exception queue with reason
`AMBIGUOUS:` (D-007). `recon.remit_bank_match` has one row per (payment, deposit), so it covers
1:1, many payments to one lockbox deposit, and one payment split across deposits (D-011).
Provider-level remittance rows (claim status `PLB`) are flagged `is_provider_level` and held as
suspense, not matched to claims (D-012). Rules and worked examples: `docs/reconciliation_rulebook.md`.

Control identity, enforced per claim line and in total, to the cent:

```
billed = paid + contractual_adjustment + denied_amount + patient_responsibility + open_balance
```

and for cash: `sum(remittance paid, by trace number) = matched bank deposits + unmatched remittance + timing differences`.

## 5. Python package `recon_engine` (in `src/`)

```
datagen/      raw-document generator and defect injector
db.py         connection handling
pipeline.py   load raw files, run sql/ in order, run close_day over the calendar
models/       one module per analysis (section 6)
reports/      figure and PDF report builders
labels.py     the five data labels and helpers to stamp outputs
cli.py        entry points
```

`python run_all.py` rebuilds everything from nothing: generate raw files, build the database,
reconcile, run every model, write outputs. `python -m pytest` runs the tests.

Output contract: every model writes `results/<name>.json` (numbers, the label of each number,
the inputs used, the seed) and figures to `figures/<name>_*.png`. Documents quote numbers only
from `results/`. `results/summary.md` is generated, never hand-written. The core writes
`results/core_build.json`, `results/control_totals.json` and `results/reconciliation.json`
(evaluation against ground truth by `recon_engine/datagen/evaluate.py`, the only package module
besides the generator that may open `data/truth/`). Models receive `cfg` from
`recon_engine.datagen.calibration.model_config()`, which excludes generator parameters (D-013).

Environment: Python 3.13 with `requirements.txt` in a virtual environment. A `.venv` inside the
repository is ignored by git; on the author's machine the repository sits in a cloud-synced folder, so
the environment lives outside it (`~/.venvs/receivables-engine`).

## 6. The seven questions and their modules

A shared building block comes first: **`models/markov.py`**. The life cycle of a claim is an
absorbing Markov chain over states such as SUBMITTED, IN_REVIEW, DENIED, APPEALED, PAID,
WRITTEN_OFF. Estimate the transition matrix from `core.fact_claim_event`, compute the
fundamental matrix `N = (I - Q)^-1` and absorption probabilities `B = N R`, by payer. Outputs
feed questions 3, 4 and 5.

| # | Who asks | Question | Module / mart | Methods |
|---|---|---|---|---|
| 1 | Hospital CFO | How much did we really collect, and where is cash stuck? | `mart.cash_position`, `mart.ar_aging`, `mart.pnl_by_payer_service` | reconciliation, aging, P&L |
| 2 | Revenue-cycle lead | Which denied claims should staff work first today? | `models/prioritize.py`, `mart.work_queue` | logistic model of overturn probability; expected recovery minus handling cost; constrained optimisation under staff hours; compared with oldest-first |
| 3 | Treasurer | Will we be short of cash in the next 13 weeks? | `models/cashflow.py`, `mart.cash_forecast` | payment-lag distribution with right censoring (Kaplan-Meier, parametric fit); Monte Carlo; cash-at-risk and CVaR; coverage backtest |
| 4 | Payer actuary | How much is still owed on claims incurred but not yet paid? | `models/reserve.py`, `mart.dev_triangle` | development triangle built in SQL; chain-ladder; bootstrap interval; frequency-severity |
| 5 | Bank credit analyst | How much can we lend against these receivables? | `models/credit.py`, `mart.borrowing_base` | eligibility and aging exclusions, concentration limits, advance rate, expected loss, interest-rate stress |
| 6 | Pharmacy manager | Which drugs lose money after reimbursement? | `models/drug.py`, `mart.drug_fifo`, `mart.drug_margin` | FIFO lot costing in SQL, expiry waste, margin per drug |
| 7 | Consulting economist | Which payers underpay against contract, by how much, and why would they? | `models/econ.py`, `mart.underpayment` | shortfall versus contract with bootstrap interval; value of float = rate x days; repeated-game reading of delay and denial; break-even appeal threshold |

Validation standard for every model:

- Fit on data before a cutoff date and evaluate after it. Tests must prove future data cannot
  change earlier outputs.
- Because the data are simulated, report two things only: how well the method recovers the
  parameters planted in the generator, and whether the decision rule behaves correctly. Do not
  describe either as a finding about real markets.
- Report weak results as weak.

## 7. Application

Streamlit app in `app/`. Each screen serves one question and one job title; there is no
"overview" screen. The first screen is the reconciliation desk: enter one claim or upload a
remittance batch and a bank statement, get the match result and the exception list at once,
and see the numbers on the other screens move. A final screen shows methods, data labels and
limits. The app must run fully offline against the embedded database.

## 8. Data labels

Every table in `mart`, every figure and every number in a document carries one label:

1. `observed_public` - measured directly in a public source.
2. `published_aggregate` - an aggregate statistic published by a public body.
3. `synthetic_record` - simulated demonstration record.
4. `financial_assumption` - an assumed business parameter (advance rate, handling cost).
5. `model_estimate` - a quantity estimated by a model in this repository.

Public data sets are never joined at record level unless they share a valid key.

## 9. File ownership (to keep parallel work from colliding)

| Area | Paths |
|---|---|
| Core | `src/recon_engine/datagen/`, `db.py`, `pipeline.py`, `labels.py`, `cli.py`, `sql/0*`-`sql/3*`, `config/`, `run_all.py`, `tests/test_core_*`, `requirements.txt` |
| Chain, cash and credit (Q3, Q5) | `models/markov.py`, `cashflow.py`, `credit.py`, `sql/models/4*`, `tests/test_markov*`, `test_cashflow*`, `test_credit*` |
| Operations and reserves (Q2, Q4) | `models/prioritize.py`, `reserve.py`, `sql/models/5*`, `tests/test_prioritize*`, `test_reserve*` |
| Drugs and economics (Q6, Q7) | `models/drug.py`, `econ.py`, `sql/models/6*`, `tests/test_drug*`, `test_econ*` |
| App and reports | `app/`, `src/recon_engine/reports/` |
| Documentation | `README.md`, `docs/` (except this file), `INTERVIEW_GUIDE.md`, `practice/` |

Each model module exposes `run(conn, cfg) -> dict`. Model SQL lives in `sql/models/`, not in
`sql/`, because `pipeline.py` runs every top-level `sql/*.sql` file; each model executes its own
SQL file from `run()`. Model authors do not edit `models/__init__.py`; the integrator adds the
`REGISTRY` lines once modules pass their tests. While building, each model area uses its own
embedded database directory (`RRE_PG_DIR=~/.cache/receivables-engine/pg-<area>`) so parallel
runs do not overwrite each other. Do not edit files outside your area; if you need a change
elsewhere, write it in `docs/requests.md`.

Do not commit. Do not push. Do not deploy. Do not create accounts.
